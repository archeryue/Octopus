# Polish pass, September 2026

> **Status:** shipped — The September 2026 polish pass: size debt, migration safety, the MCP sidecar footprint, gates, docs, and monitoring. All eleven items in §10 landed; what changed, and the four defects the pass found, is in [`../2026-09-25-polish-pass.md`](../2026-09-25-polish-pass.md).

## 1. Why this document

Octopus is seven months old, 218 commits, effectively single-author, and
still accelerating — 36 commits in the last 30 days, almost all feature
work. Nothing is broken. The purpose of this pass is to pay down the
specific debts that *accumulate invisibly* under that kind of velocity:
a class that grew past the point of comprehension, a migration mechanism
that swallows its own failures, a context file that spends half its bytes
on a hand-maintained inventory, and the total absence of any historical
record of how the system actually behaves while it runs.

Every claim below is measured, not estimated. Measurements were taken on
2026-09-24/25 against the live process table and the production database
(`~/octopus.db`, 82.9 MB = 79.1 MiB). Byte counts in this
document are decimal (MB) unless suffixed MiB. Where a number is cited it can be
re-derived; where a proposal is speculative it says so.

Scope: backend (`server/`, 27,899 lines), tests (`tests/`, 26,203 lines),
docs (`docs/`, 9,077 lines), `CLAUDE.md`, and project tooling. The
frontend (`web/`, 27,607 lines) is touched only where it must follow a
backend change (§5 B2) or where a gate is missing (§8 F2).

## 2. What is already right

The plan must not damage any of this:

- **The harness contract holds.** `server/harness/` (11 files, 3,279
  lines) genuinely isolates backend specifics. Capabilities are *derived*
  from `RuntimeProfile` rather than tracked in a hand-maintained flag
  matrix, and `Harness` has no subclasses. There is no `if backend ==`
  anywhere outside that package.
- **API contracts are generated, not hand-written.**
  `web/src/api/contracts.ts` (6,206 lines) comes from the OpenAPI schema
  via `bun run generate:contracts`. Both sides last changed 2026-09-21 —
  currently in sync.
- **The real-CLI test gate is thoughtfully built.** `tests/cli_gate.py`
  probes whether a CLI is *usable* (a real `--print` call must exit 0),
  not merely present, precisely so a lapsed login reads as a skip rather
  than a false regression.
- **Error handling is disciplined.** Zero bare `except:` in 27,899 lines.
  89% of functions carry return annotations. Only 9 `type: ignore`.
- **Function size is not a general problem.** Of 985 functions, 965 are
  under 100 lines. The size debt is concentrated in ~6 places (§3 A1).
- **The test suite is real.** 1,181 tests, of which 1,147 are hermetic
  and pass in 34.1 s at 314 MB peak RSS. This is what makes the riskier
  items in this plan safe to attempt at all.

## 3. Architecture

### A1 — `SessionManager` is a 4,004-line class with 84 methods

It carries at least eight responsibilities: session lifecycle, fork and
duplicate, archive/unarchive, import/export, per-turn message driving,
backend process supervision, credential resolution and OAuth refresh, and
held-process reaping. The size debt of the whole backend is concentrated
here:

| Function | Lines | Location |
|---|---|---|
| `_run_backend` | 485 | `server/session_manager.py:2135` |
| `fork_session` | 249 | `server/session_manager.py:551` |
| `duplicate_session` | 183 | `server/session_manager.py:838` |
| `send_message` | 148 | `server/session_manager.py:1862` |

For comparison, the next-largest function anywhere else in `server/` is
`bg_tasks._run_task` at 217 lines. Across the backend, 20 functions
exceed 100 lines and 4 exceed 200.

**Proposal.** Extract along seams that already exist implicitly, one
extraction per unit of work, behavior unchanged:

1. `CredentialResolver` — `_resolve_credential`,
   `resolve_credential_by_id`, `_refresh_oauth_if_needed` (~250 lines).
   Smallest and most self-contained; do it first as the pattern-setter.
2. `ForkService` — fork, duplicate, preview, incomplete-fork recovery.
   Much of the logic already lives in `fork_helpers.py` (540 lines), so
   this is largely a matter of moving the orchestration next to it.
3. `ProcessPool` — `_enforce_held_cap`, `reap_held_processes`,
   `_reaper_loop`, `start_reaper`, `stop_reaper`,
   `stop_all_held_processes`.
4. `SessionLifecycle` — create, archive, unarchive, delete, import,
   auto-archive, evict.
5. `_run_backend` — split into the event-dispatch loop plus one handler
   per `HarnessEvent.type`. The event vocabulary is already normalized
   and enumerated in `harness/events.py`, so the handler set is defined
   by an existing contract rather than invented here.

Target: `SessionManager` under 1,200 lines, acting as a coordinator.
`tests/test_session_manager.py` is the largest test file in the repo at
85 tests, which is the safety net that makes this tractable.

### A2 — import-time singleton

`session_manager = SessionManager()` at `server/session_manager.py:4004`,
imported directly by 18 modules. Test isolation therefore depends on
manual reset, and the object cannot be instantiated twice in one process.

**Proposal.** Keep the module-level singleton as a compatibility shim so
nothing breaks at once, but have routers obtain it through a FastAPI
dependency (`Depends(get_session_manager)`). Mechanical, and it is what
makes A1's extractions injectable rather than merely relocated.

### A3 — migrations swallow their own failures

`Database._apply_migrations` (`server/database.py:423`) is 202 lines of:

```python
try:
    await self._conn.execute("ALTER TABLE sessions ADD COLUMN ...")
except Exception:
    pass
```

The comment explains the intent — SQLite has no `ADD COLUMN IF NOT
EXISTS`, so a re-run must tolerate "column already exists". But a bare
`except Exception` equally absorbs a misspelled column, a wrong table
name, a locked database, a constraint violation, and a full disk. A
broken new migration silently no-ops and resurfaces later as an
inexplicable missing column. There is **no schema-version ledger**, so
nothing records what has run.

This is also the largest cluster of the 26 `except Exception: pass` sites
in `server/` (§8 F4).

**Observed, not hypothesised.** A routine `scripts/check.sh` run on
2026-09-25 surfaced `sqlite3.OperationalError: duplicate column name:
delegation_request` out of `tests/test_bg_tasks.py`, raised by the
`ALTER TABLE sessions ADD COLUMN delegation_request TEXT` at
`database.py:564` and absorbed by the handler at `database.py:566`. That
is the benign case the swallow exists for, so nothing was broken — but it
is the mechanism running indiscriminately in plain sight, and the only
reason it was visible at all is that it happened to escape as a GC-time
`PytestUnraisableExceptionWarning`. A typo'd column name, a locked
database or a full disk would have produced exactly the same silence,
with no warning to notice. (A further 32 handlers catch a *narrower* type and
still only `pass`; those are out of scope here — a narrow catch is a
stated intent, not a swallow.)

**Proposal.** A `schema_migrations(version, applied_at)` table; numbered
migration functions, each applied exactly once inside an explicit
transaction; column existence tested with `PRAGMA table_info` rather than
inferred from an exception, so genuine failures raise.

**The backfill must validate, never assume.** The naive version — create
the ledger, stamp it at current head — is unsafe *precisely because* the
current migrator swallows failures: an existing database may be only
partially migrated, and stamping head would permanently record a missing
column as applied, making the gap unrepairable. The sequence must be:

1. create `schema_migrations`;
2. introspect actual schema via `PRAGMA table_info` and `sqlite_master`
   (16 user tables, 10 explicit indexes on the production DB);
3. *repair* any missing additive migration;
4. only then stamp the ledger, and only for what verifiably exists.

**Three migrations are destructive rebuilds, not additive.** `schedules`
is rebuilt twice (`database.py:665`, `database.py:806`) and
`bridge_mappings` once (`database.py:842`), each via
`CREATE TABLE …__new` → `INSERT … SELECT` → `DROP TABLE` → `RENAME TO`.
These are the *well-built* ones — each is guarded by a shape probe
(`_column_is_not_null`) rather than by exception swallowing, so they run
exactly once. But two properties matter for the ledger:

- they cannot be re-run idempotently the way an `ADD COLUMN` can, so the
  ledger must model them as versioned steps with their shape probe as the
  verification predicate, not as "add column if absent";
- they run through `executescript`, which issues an implicit `COMMIT`
  before executing and leaves the script's own statements
  auto-committing. A failure between `DROP TABLE schedules` and
  `RENAME TO schedules` therefore loses the table. Low probability, and
  it has already succeeded on the production database — but the new
  migrator must wrap rebuilds in an explicit transaction rather than
  inherit this window.

The 82.9 MB production DB must migrate in place, never reset, and step 2
must be rehearsed against a *copy* of it before the change lands —
a unit test on a fresh schema cannot exercise the partially-migrated
case that makes this risky.

**This finishes a transition already under way, rather than starting
one.** Migrations live in four methods, and they are not uniform in
quality:

| Method | Lines | Shape |
|---|---|---|
| `_apply_migrations` (L423) | 202 | 24 `ALTER`, 1 `CREATE TABLE`, 1 `CREATE INDEX`, 1 backfill — the `try`/`except Exception: pass` style |
| `_migrate_schedule_recurrence` (L649) | 44 | a rebuild: `CREATE`/`INSERT…SELECT`/`DROP`/`RENAME` |
| `_migrate_schedule_run_at` (L694) | 15 | 2 `ALTER` |
| `_migrate_agents` (L724) | 132 | 2 rebuilds + 6 data backfills |

Crucially, `_has_column` already exists and is used at **7** sites, and
`_column_is_not_null` at 2 — all in the *later* three methods. The
swallow-everything pattern is the older style; the newer migrations
already introspect before acting. A3's job is therefore to (a) extend
that existing predicate to the 24 `ALTER`s still guarded by exception
swallowing, and (b) add the ledger those four methods currently lack.
The 20 `ADD COLUMN` steps in `_apply_migrations` are the actual work:

`sessions`: credential_id, archived, backend, parent_session_id,
delegation_request, app_id, forked_from_session_id, fork_after_seq,
fork_needs_replay, fork_metadata, fork_revert_record, fork_status ·
`messages`: attachments, git_head, git_status_clean ·
`agents`: backend, subagents · `backend_credentials`: token_expires_at ·
`applications`: icon_src · `bridge_mappings`: verbose

### A4 — `database.py` is 2,600 lines

It holds the schema string, all migrations, and the data-access layer for
all 17 tables.

**Proposal.** Split into `schema.py`, `migrations/` (one module per
version, following A3), and per-domain repositories. Incremental — one
table group at a time — and a natural continuation of A3 rather than a
separate campaign.

## 4. Performance

Measured on the live system with PSS (proportional set size), so shared
pages are not double-counted. The sidecar total is a *rate*, not a
constant — seven processes spawn per active session — so it is stated
per-session, with two independent snapshots as corroboration:

| Component | Cost |
|---|---|
| MCP sidecars (`python3 -m server.mcp_servers.*`) | **~39 MB PSS each, 7 per session** |
| — snapshot A (2 sessions) | 14 procs, ~550 MB |
| — snapshot B (same day, busier) | 27 procs, ~1.04 GiB |
| — snapshot C (`measure-footprint.py`) | 21 procs, 831 MB, mean **39.6 MB** |
| `claude --print` subprocess | ~200–290 MB PSS each |
| `octopus serve` | 118 MB PSS (stable) |

The per-session figure is what the plan relies on; the snapshots differ
only because session count does. Any restatement of this table should
quote the rate, not a total.

The controller is cheaper than a single one of the CLI processes it
supervises. CPU is negligible throughout (`octopus serve` at 0.1%).
There is no compute in this program: 503 `async def`, 1,141 `await`, 43
subprocess spawns, and zero uses of numpy, pandas, multiprocessing or any
thread pool. Every user-visible wait is a model generating tokens.

Consequently this section contains no proposal that trades clarity for
speed. The wins available are structural.

### B1 — the MCP sidecar fan-out is ~85% of Octopus's own footprint

Seven Python interpreters are spawned **per session**, ~39 MB PSS each,
each an idle stdio-to-HTTP proxy that forwards to `127.0.0.1:8080`.
Importing one sidecar module costs **~247 ms** (best of three via
`scripts/measure-footprint.py`; a single cold run reads ~455 ms, which is
cache noise rather than the real cost), paid seven times on the
session-start path for ~1.7 s. The entire package is 1,968 lines.

The sidecar *share* of Octopus's own memory rises with session count,
because the server's 119 MB is flat while sidecars are per-session: 82%
at two sessions, 87% at three. Quote the per-session rate, not the
share.

**Proposal.** Serve the tool namespaces from the main application over
MCP streamable-HTTP, taking the sidecar count to **zero**. Register them
per-namespace so tool names stay byte-identical — `mcp__bg__run` must
remain `mcp__bg__run`. This constraint is load-bearing: consolidating
seven servers into one process instead would renumber every tool to
`mcp__octopus__*` and invalidate every system prompt that documents them,
including Octopus's own injected prompt.

Expected recovery: ~39 MB × 7 per session (~550 MB at two sessions,
~830 MB at three) and ~1.7 s of session-start latency.

**The actual risk is identity, not naming.** Naming is fine: both CLIs
expose tools as `mcp__<server-key>__<tool-name>`, so preserving the keys
(`bg`, `ask`, `ask_agent`, `research`, `schedule`, and the per-installation
connector keys) preserves every tool name. Transport is fine too: the
`mcp` Python SDK provides `FastMCP.run_streamable_http_async` /
`streamable_http_app`, Claude Code accepts `--transport http`, and Codex
accepts `codex mcp add --url`.

What does not survive the move is **per-session identity**. Today each
sidecar is handed `OCTOPUS_SESSION_ID`, `OCTOPUS_INSTALLATION_ID` and
`OCTOPUS_AUTH_TOKEN` as environment variables at spawn time, which is how
`mcp__bg__run` knows which session to attach a task to. A single shared
HTTP endpoint has no equivalent — every session's calls arrive at the same
socket. This must be solved explicitly, by session-scoped URL paths
(`/mcp/{session_id}/bg`) or per-session bearer credentials, and it is the
part most likely to be wrong on the first attempt.

Three further consequences, none of which exist today:

- **Failure domain.** A sidecar that hangs or crashes today takes only
  itself down. An in-process tool handler contends with the API event
  loop. B1 must add per-call timeouts and bounded concurrency around tool
  execution, or it trades 550 MB for a new class of outage.
- **Auth scope.** The sidecars currently receive the master
  `OCTOPUS_AUTH_TOKEN`. Long-lived master-token bearers on an HTTP
  endpoint are a downgrade; issue per-session scoped tokens instead.
- **Spike first.** §10 puts a compatibility spike ahead of the
  implementation. **It has now run, and B1 is GO** — with one design
  constraint the spike discovered.

**Spike results (2026-09-25).** A throwaway FastMCP streamable-HTTP server
serving namespace key `bg`, driven by the real CLIs:

- *Transport works.* Claude Code accepts `{"type": "http", "url": …}` in
  `--mcp-config` and performs full MCP discovery over it
  (`ListTools`/`ListPrompts`/`ListResources` all arrive). Codex accepts
  `-c mcp_servers.<key>.url`.
- *Naming survives, on both backends, for two different reasons.* On
  Claude Code the CLI itself advertised `mcp__bg__whoami` and the model
  called it by that name. On Codex the name is **Octopus's own
  construction**: a `mcp_tool_call` event carries `server` and `tool` as
  separate structured fields, and `codex.py:413` builds
  `f"mcp__{server}__{tool}"` from them. Codex's human-readable output
  displays the same call as `bg/whoami`, which is easy to mistake for a
  naming change — it is a display format, not a tool name, and production
  data confirms the parser has always recorded `mcp__bg__run` for stdio
  Codex sessions. Naming is therefore transport-independent on Codex and
  transport-preserved on Claude; keeping the server key is sufficient for
  both, which is what rules out consolidating seven servers into one and
  rules *in* per-namespace registration.
- *The bearer arrives on Codex.* `authorization: Bearer <token>` reached
  the tool, alongside `accept`, `content-type`, `content-length` and
  `host` — so the identity mechanism below is confirmed on the backend
  that constrains it, not just on the permissive one.
- *A tool can see its own HTTP request.* `ctx.request_context.request` is
  a live Starlette `Request` exposing `headers` and `url`. There is no
  module-level `get_http_request` helper in mcp 1.26.0, which is easy to
  misread as the capability being absent. Both header- and path-based
  identity are therefore available, with no auth middleware wired —
  `get_access_token()` returns `None` until one is.

**The design constraint: identity must ride in the bearer token.** Claude
Code accepts arbitrary per-server `headers`; Codex does not. `codex mcp
add --env` is documented "Only valid with stdio servers", and the sole
per-server injection point for an HTTP server is
`--bearer-token-env-var`. A custom `X-Octopus-Session` header would thus
work on Claude and be impossible on Codex — a capability difference
inside the harness, which is precisely what the harness contract exists
to prevent.

So a session-scoped **bearer token carries the identity**: Octopus mints
one per session, the server resolves it to `(session_id,
installation_id)`, and each profile passes it its own way (Claude: an
`Authorization` header in the config JSON; Codex: an env var named by
`bearer_token_env_var`). This replaces the `OCTOPUS_SESSION_ID`,
`OCTOPUS_INSTALLATION_ID` and `OCTOPUS_AUTH_TOKEN` env vars that stdio
spawning supplies today, and settles the auth-scope concern above in the
same move: no long-lived master token on an HTTP endpoint, because the
credential is per-session by construction.

`McpServerEntry` (`server/harness/profile.py:29`) is stdio-only today
(`key`, `command`, `args`, `env`). It gains an HTTP variant carrying
`url` plus the session token; `claude_code.py:253` and `codex.py:122`
each render it their own way, which is where the asymmetry belongs.

### B2 — `GET /sessions/{session_id}` returns the whole transcript

`Database.load_messages` (`server/database.py:1096`) accepts `limit` and
`offset`, and **all twelve call sites pass neither** (nine in
`session_manager.py` / `fork_helpers.py` / `app_agent.py`, three in
`routers/`). No pagination is plumbed through the frontend.

Production data: 46,448 messages across 66 sessions. Worst session
`6cc717e13c0e` holds 4,613 messages / 5.5 MB; `fe8fa0e1e6d4` holds 4,873.
Per-message size is p50 ≈ 0 KB, p95 4.4 KB, p99 16.2 KB, max **1.1 MB** —
the tail is a handful of large tool outputs, not uniform growth.

**Proposal.** Window the initial fetch to the most recent N messages
(200 covers the great majority of sessions), add a `before_seq` cursor
for scroll-back, and have `ChatView` request older pages on demand. The
existing `idx_messages_session(session_id, seq)` index already makes this
a cheap range scan, so no schema change is required.

The risk in B2 is not the query, it is the client. Windowed transcripts
plus load-older regress scroll anchoring and duplicate-`seq` handling
almost by default, and `ChatView.tsx` is 1,579 lines. B2 is not done
without frontend tests that assert scroll position survives a page load
and that no message renders twice across a boundary.

### B3 — fork replay filters in Python what SQL could filter

`session_manager.py:1966` loads every message in the session and then
discards those above `fork_after_seq` in a list comprehension, while
`database.py:987` already contains a `WHERE session_id = ? AND seq <= ?`
query. Guarded by `fork_needs_replay`, so this is first-turn-after-fork
only, not per turn. Small and pure.

### B4 — no periodic commit; a crash costs a turn of transcript

`append_message` sets `_dirty = True` and defers the commit
(`server/database.py:1094`). Only three real `flush()` call sites exist
(`session_manager.py:1211`, `session_manager.py:2003`,
`bridges/base.py:208`) and there is no timer task. The production WAL
currently sits at 7 MB, which is this batching visible on disk.

Those three are the *explicit* flushes. `load_messages` also calls
`await self.flush()` on entry (`database.py:1100`, commented "ensure
pending writes are visible"), so any read path commits as a side effect.
The exposure is therefore narrower than "a turn": it is everything
appended since the last write-visibility flush, with no read in between.
That is still unbounded, and a long tool-heavy turn with no intervening
read is exactly the case that loses the most.

The batching itself is a sound trade for a high-frequency append path.
It is simply untimed.

**Proposal.** Flush on whichever comes first — approximately 500 ms or 32
pending messages — so a hard kill costs sub-second rather than a whole
turn. Document the durability guarantee explicitly where `_dirty` is set.

### B5 — SQLite configuration and indexes

Only two pragmas are set (`journal_mode=WAL`, `foreign_keys=ON`). There
is no `busy_timeout`, and `synchronous` is left at its default. The
production database has 16 user tables and 10 explicit indexes.

**Proposal.** Set `busy_timeout` and an explicit `synchronous`. Audit the
7 indexes against actual query predicates — the hot one
(`idx_messages_session`) is correct; the gap, if any, is on
`sessions(agent_id)` and `schedules(agent_id)`, which should be confirmed
with `EXPLAIN QUERY PLAN` before adding anything. Do not add indexes
speculatively.

## 5. Tests and the local gate

### C1 — the four-suite ritual is honour-system (no CI, by choice)

`CLAUDE.md` requires four suites after every change: backend pytest,
frontend vitest, `tsc --noEmit`, and Playwright e2e. `lefthook.yml`
enforces only two of them, and conditionally: pytest when `server/` or
`tests/` change, `tsc` when `web/src/**` changes. vitest and eslint are
never run by any gate.

GitHub Actions is explicitly out of scope — this project does not want
hosted CI.

**Proposal.** A single `scripts/check.sh` that runs all four gates in one
command, and an extension of `lefthook.yml` to also run vitest (on
`web/src/**`) and eslint. The hermetic backend tier measures 34.1 s, so a
per-commit gate remains usable. E2E stays manual — it takes ~4.5 min and
needs real CLIs.

### C2 — the real-CLI tier has no name, and probes during collection

13 files require a signed-in `claude` and/or `codex`, covering only **34
of 1,181 tests** (2.9%). Excluding them today requires a hand-written
13-entry `--ignore` list.

Worse, the gate is evaluated at *module* level — e.g.
`pytestmark = pytest.mark.skipif(not claude_cli_works(), ...)` in
`tests/test_backend_claude_code_real.py:33`, and
`HAS_CLAUDE = claude_cli_works()` in `tests/test_app_agent_real.py:37`.
Because `claude_cli_works()` spawns a real `claude --print` call, plain
collection has a side effect of invoking the model. Measured: hermetic
collection is **0.80 s**; full collection is **16.44 s**. The ~15.6 s
difference is the probe.

**Proposal.** Register markers `real`, `real_claude`, `real_codex` in
`pyproject.toml`. Each real file declares markers instead of computing a
skip condition. A `pytest_runtest_setup` hook in `tests/conftest.py`
consults `cli_gate` lazily, so the probe fires only when a real test is
actually about to run. Then:

- hermetic tier: `pytest -m "not real"` — replaces the `--ignore` list
- collection becomes side-effect-free
- `scripts/check.sh` and `lefthook` use the marker expression

One change removes three problems.

### C3 — one deprecation warning

`tests/test_applications.py::test_static_accepts_query_token_and_cookie`
emits two `httpx` `DeprecationWarning`s (per-request `cookies=` is
deprecated in favour of setting them on the client). Harmless now; a
failure when httpx removes it.

## 6. Documentation

### D1 — `docs/architecture.md` is three months stale

shipped in that window and entirely absent from the document:

### D2 — 30 documents with no status

`docs/plans/` mixes shipped designs, in-progress designs and superseded
ones with no way to tell them apart from the outside.

**Proposal.** A `Status: shipped | in-progress | superseded by X` header
line per plan, and a generated table in `docs/README.md`.

### D3 — plan documents are doing reference duty

`session-rewind.md` is 1,851 lines; `connectors.md` 1,076. As *design*
records that is appropriate. The problem is that they are also the only
place the durable facts live, which is the mechanism by which
`architecture.md` rotted (D1): new work documented its design and there
was no step that promoted the lasting parts upward.

**Proposal.** Keep plans as historical design records. Promote durable
structure into `architecture.md` as part of finishing a feature, which
the D1 lefthook nag prompts.

## 7. `CLAUDE.md`

### E1 — half the file is three table rows

32,512 bytes over 166 lines. Lines 68, 69 and 70 are **9,816 / 3,682 /
2,334 characters** — single markdown table cells enumerating in prose
what every test covers. Together, 15,832 bytes: **49% of the file**.

They are unreadable as a table, they are loaded into every session's
context, and they must be hand-edited whenever a test is added. (The
counts themselves are currently *accurate* — the file says 1,181 backend
tests and the suite collects exactly 1,181. This is not a drift report;
it is a cost and legibility report.)

**Proposal.** Replace the three rows with a four-row summary — suite,
command, count, one-line scope — and point to `pytest --collect-only` for
detail. Recovers roughly 16 KB of every session's context budget.

### E2 — the largest sections have no sub-structure

Seven `##` headings across 166 lines, with "Project Structure" and
"Conventions" carrying most of the payload in very long bullets; ten
bullets exceed 570 characters.

**Proposal.** `###` sub-headings so a session can skim to the rule it
needs rather than reading linearly.

## 8. Tooling hygiene

### F1 — 27,899 lines of annotated Python with nothing checking it

Neither `ruff`, `mypy` nor any formatter is installed or configured, and
`pyproject.toml` carries no tool configuration. The annotations are
thorough — 89% return coverage, 293 `Any`, 9 `type: ignore` — and
entirely unverified. They are documentation, not a safety net.

**Proposal.** Add `ruff` (lint + format) and `mypy` in non-strict mode.
Baseline existing findings rather than fixing all of them at once, then
ratchet. This should land *before* A1: a type checker is what makes a
4,000-line class extraction safe to perform quickly.

Keep the initial `mypy` configuration deliberately narrow — `server/`
only, generated and frontend artifacts excluded, no `--strict`, errors
baselined rather than blocking. A broad first configuration on 27,899
untyped-checked lines becomes a tarpit that stalls A1 instead of enabling
it, which would invert the reason for doing F1 at all.

### F2 — eslint is configured but ungated

`web/package.json` defines `lint: eslint .`; no hook or script runs it.
Folded into C1's `scripts/check.sh`.

### F3 — contract generation is manual

`generate:contracts` must be remembered. It is currently in sync by
discipline alone. **Proposal.** `scripts/check.sh` regenerates and fails
on diff.

### F4 — 26 silent `except Exception: pass`

The majority are A3's migrations. The remainder deserve a case-by-case
pass: either log, or narrow the caught type. **Proposal.** Handle the
migration cluster in A3; sweep the rest afterwards, since each needs an
individual judgement rather than a rule.

## 9. Monitoring

### G0 — the motivating case

The Gmail connector was unavailable for **eleven consecutive days**. A
daily schedule fired on each of them, failed on each of them with
`connector unavailable`, and nothing counted it. `_shared.py` even
provides `mark_needs_reconnect(error_code="invalid_grant")`, so the
*mechanism* to record a broken connector exists; what is missing is any
durable record of repeated failure. That is the gap this section closes.

### G1 — instrumentation rides an existing seam

`HarnessEvent` (`server/harness/events.py`) already carries `cost`,
`duration_ms` and `num_turns`, and already normalizes `result` and
`error` across both backends. `SubagentUpdate` already carries `tokens`,
`tool_uses` and `duration_ms`. Turn-level metrics therefore require **no
backend-specific code**: tapping the normalized event stream satisfies
the harness-abstraction rule by construction rather than by vigilance.

Seven hook points, all at chokepoints that already exist:

| Hook | Location | Answers |
|---|---|---|
| turn lifecycle | `harness/run.py` event stream | latency p50/p95/p99, cost, tokens, error class (reusing `is_auth_error` / `is_transient_error` / `is_stale_session_error`), retries, premature-exit respawns |
| tool calls | `mcp_servers/connectors/_shared.py` | **G0** — consecutive failures per connector |
| bg tasks | `bg_tasks.py:_run_task` | duration, exit code, wall-clock-cap hits |
| schedule fires | `scheduler.py:_fire` | fires, stacking-guard skips, outcomes |
| delegations | `delegations.py` | depth, fan-out, time-to-reply, cascade cancels |
| db flush | `database.py:flush` | pending count and lag — measures B4 |
| http | existing middleware at `main.py:166` | latency by route *template* |
| turn queue | `session_manager.start_message` / `QueuedPrompt` | **wait time before a turn starts** — invisible today |
| turn termination | `interrupt`, `_safe_backend_interrupt` | interrupted and cancelled turns, not only completed ones |
| held processes | `_enforce_held_cap`, `reap_held_processes`, `stop_all_held_processes` | reuse hit rate, reap and stop *failures* |
| MCP tool dispatch | each `mcp_servers/*` entry point | latency and error rate per namespace *and* per tool, not just per connector |
| OAuth refresh | `_refresh_oauth_if_needed`, `mark_needs_reconnect` | refresh attempts, failures, `needs_reconnect` transitions — the other half of G0 |
| app backends | `app_backends.py` | supervised-process start, proxy errors, crash, reap |
| delegation terminal state | `delegations.py` | not just time-to-reply but how it *ended* — reply, question, error, cascade-cancel |
| WAL / checkpoint | `database.py` | WAL size growth and checkpoint failures, alongside flush lag |

Plus a periodic sampler (30–60 s): RSS for the server, each spawned CLI
and each MCP sidecar; held-process count; WAL size; database size. That
sampler is what will prove B1's ~550 MB and then measure its removal.

Route templates, not raw paths, and connector *names*, not full URLs —
label cardinality must stay bounded by construction.

### G2 — storage: a separate SQLite database

`octopus.db` is already 82.9 MB with no retention policy. High-frequency
metrics do not belong in it.

`octopus-metrics.db`, WAL, two tables:

- `events(ts, kind, session_id, agent_id, backend, duration_ms, ok,
  error_code, detail_json)`, indexed on `(kind, ts)` and `(ts)`
- `samples(ts, metric, value, labels)` for the periodic gauges

It is independently prunable, can be deleted without touching application
state, and a defect in metrics collection cannot corrupt session data.
**Retention is 30 days**, swept by Octopus's existing durable scheduler —
no cron, no new subsystem.

SQLite-only: no external metrics store, no Endlex mirror. The dimensional
`(kind, error_code, backend, agent_id)` shape is the whole point, and it
is a SQL shape.

### G3 — the sink must never be able to break a turn

`record(kind, **fields)` appends to a bounded in-memory deque and
returns; one async writer batches inserts. Drop-oldest under sustained
backpressure. The write path swallows and logs — this is the single place
in the codebase where catching broadly is correct, and the comment must
say so explicitly, so it does not read like the F4 swallows being removed
elsewhere.

### G4 — analysis is the deliverable

Collection is worthless without a query surface, and this one exists to
be read weeks later:

- `octopus monitor turns|errors|tools|resources|schedules --since 7d` —
  canned SQL, formatted tables. The primary interface.
- `/api/monitor/*` plus a page in the web UI for live numbers.
- Plain `sqlite3 octopus-metrics.db` for anything ad hoc — which is the
  reason the dimensional shape matters.

### G5 — scope of v1

v1 is a complete vertical slice, not a partial one: the sink, the schema,
30-day retention, **all seven hook points**, the periodic sampler, the
`octopus monitor` CLI, and the API plus page. Fully tested, no TODOs.

## 10. Order of work

1. **C2** — markers. Removes the `--ignore` list and the 15.6 s
   collection probe; every later item's test loop gets faster and
   side-effect-free.
2. **C1 + F2 + F3** — `scripts/check.sh` and the lefthook extension.
   Builds directly on C2's marker expression.
3. **B0** — `scripts/measure-footprint.py` (done): records sidecar
   count, per-process PSS, namespaces-per-session, and sidecar import
   cost, with `--json` for diffing runs. It earned its place immediately
   by correcting the session-start figure above from ~3 s to ~1.7 s.
   Deleted, or absorbed into G's periodic sampler, once G lands.
4. **B1 spike** — prove the three legs before committing to the change:
   both CLIs reach one local streamable-HTTP endpoint; session-scoped
   routing replaces the `OCTOPUS_SESSION_ID` env var; `mcp__bg__run`
   keeps its name and attaches to the right session. Stop here if any
   leg fails.
5. **B1** — MCP sidecars to streamable-HTTP, with the per-call timeouts,
   bounded concurrency and scoped tokens §4 B1 requires.
6. **F1** — ruff and mypy (narrow config), wired into `scripts/check.sh`.
7. **A3 + A4** — migration ledger (validate-then-stamp, rebuilds
   modelled, rehearsed against a copy of the production DB) and the
   `database.py` split. The one genuine correctness risk in the codebase.
8. **B2 + B3 + B4 + B5** — pagination (with the frontend scroll tests),
   SQL filter, timed flush, pragmas. Small, independent, user-visible.
9. **A1 + A2** — the `SessionManager` extraction, one component per unit
   of work. Requires F1 landed.
10. **D + E** — documentation and `CLAUDE.md`. E1 is a twenty-minute win
    and may be pulled forward at any time.
11. **G** — monitoring, as a complete slice.

On the ordering of G: placing it last means the hooks are written once,
into the homes A1/A3/A4 leave behind, rather than into
`session_manager.py` and `database.py` immediately before both are
rewritten. The cost is that the intervening items have no instrumented
baseline. B0 buys that back for the one item where it matters most (B1)
at a fraction of G's cost, which is why a throwaway script earns its
place in an otherwise no-shortcuts plan: it is scaffolding with a stated
demolition date, not a deferred obligation.

Note on §3 A1 and the "Do It Right The First Time" rule: a 4,004-line
class cannot be decomposed perfectly in one sitting. Each *extraction*
(A1.1 … A1.5) is therefore its own complete unit — fully done, tests
green, no TODOs, no follow-up notes. "Refactor SessionManager" is a
programme, not a task. This honours the rule without requiring a single
heroic change.

## 11. What this defers

- **Alerting and thresholds on monitor data.** Needs real collected data
  first: there is currently no basis for deciding what a bad p95 or an
  abnormal failure rate looks like for this system. Revisit after 30 days
  of `octopus-metrics.db`.
- **A message retention policy for `octopus.db`.** 46,448 messages and
  82.9 MB with no pruning is a real trajectory, but message history is
  product data, and deleting it is a user-facing decision, not a
  cleanup. B2's pagination removes the performance symptom; the policy
  question is deliberately left open.
- **Rewriting any part of Octopus in another language.** Assessed and
  rejected on 2026-09-24: the workload is pure async I/O orchestration,
  CPU is negligible, and the controller is already cheaper than one of
  the CLI processes it supervises. B1 captures the only footprint win
  that was actually available, and captures it in Python.
- **E2E tests in an automated gate.** ~4.5 minutes and real CLIs
  required. Stays a manual pre-release step.
- **Splitting `web/src/components/ChatView.tsx`** (1,579 lines). Real,
  but out of scope for a backend-focused pass; it should be assessed on
  its own terms after B2 changes how messages arrive.
- **`SessionManager.db`'s initialization contract.** F1's last mypy code,
  `union-attr`, is now 26 errors and every one of them is that single
  attribute: typed `Database | None` because it is assigned in
  `initialize()` rather than `__init__`. The 16 errors that were *not*
  that attribute are fixed. Closing the rest means one decision across
  203 `self.db` reads, 46 of which guard with `if self.db:` — an
  asserting property turns those 46 silent skips into raises. That is
  arguably more correct (a write that quietly does nothing is worse than
  one that fails loudly) and it is unarguably a change in production
  failure modes, so it is a call to make deliberately with its own
  verification, not a tidy-up to fold into a polish pass. Everything
  needed to decide it is measured above.
